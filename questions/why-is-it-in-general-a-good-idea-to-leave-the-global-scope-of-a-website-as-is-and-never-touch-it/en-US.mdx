1. The global scope is shared by everyone

Every script on the page (your code, third-party libraries, browser extensions, analytics snippets, ads, etc.) shares the same global namespace:

If you define global variables or functions, you risk naming collisions.

Another script might accidentally overwrite your globals, or vice-versa.

This results in hard-to-debug bugs that depend on load order or external scripts you don’t control.

2. Globals persist for the lifetime of the page

A global variable:

Never goes out of scope until the tab is closed.

Cannot be garbage-collected early.

Stays in memory even if you don’t need it anymore.

This leads to increased memory usage and makes it easier for accidental references to stick around.

3. It reduces modularity and increases coupling

When everything is in the global scope:

Modules depend on invisible global state.

Changing or removing a piece of code can break unrelated parts.

Refactoring becomes dangerous.

Modern development encourages encapsulation, where modules keep their internal details private.

4. It makes code harder to reuse

Code that depends on globals is:

Hard to extract and use elsewhere.

Hard to test (you have to reset global state between tests).

Impossible to run multiple instances of.

This severely impacts maintainability and flexibility.

5. It breaks the principle of least surprise

Developers expect the global scope to contain only standard browser objects (e.g., window, document, Date, Array, etc.).

If you add your own properties—especially innocuous names like helpers, utils, or data—you surprise future maintainers and cause subtle breakage.

6. Global pollution can cause compatibility issues in the future

Browsers continue to add new global names (e.g., fetch, URL, CSS, Notification, etc.).

If you create a global with a name that the browser later adopts, your code may suddenly break in a future update.

7. Third-party libraries assume the global scope is clean

Many libraries (jQuery plugins, analytics tools, etc.) look for specific globals or define their own. If you override one or interfere with these, the result is unpredictable failures.

So what should you do instead?
✔ Use modules (import/export)

ES modules provide true encapsulation and are the modern standard.

✔ Use closures or IIFEs in non-module environments

These create private scopes that don’t leak variables.

✔ Attach intentional globals explicitly if needed
